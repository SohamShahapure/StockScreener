# Deployment guide (Phase 11)

Production topology:

```
Vercel (Next.js frontend)  ──HTTPS──▶  Render (FastAPI backend)
                                            ├── Render PostgreSQL  (users, watchlists, caches)
                                            └── ChromaDB on a persistent disk (RAG index)
LLM: Groq hosted API (fast, free tier)
```

Nothing in the app code is environment-specific — everything below is
configuration. Do the backend first (the frontend needs its URL).

---

## 1. Backend + database on Render

1. Push this repo to GitHub (the root `.gitignore` keeps `.env`, `venv/`,
   `*.db`, `chroma_db/`, and `node_modules/` out of the commit).
2. In Render: **New + → Blueprint**, select the repo. Render reads
   [`render.yaml`](render.yaml) and provisions the web service **and** a
   managed Postgres database, wiring `DATABASE_URL` between them for you.
3. When prompted (or under the service's **Environment** tab), fill in the
   `sync:false` secrets:
   | Key | Value |
   |---|---|
   | `GROQ_API_KEY` | your key from https://console.groq.com/keys |
   | `CORS_ORIGINS` | `["https://<your-app>.vercel.app"]` (fill in after step 2) |
   | `NEWS_API_KEY` | optional — enables the news tab |
   `SECRET_KEY` is auto-generated by Render; `DATABASE_URL` is auto-injected.
4. Deploy. The first build installs the ML deps (a few minutes). Confirm
   `https://<service>.onrender.com/` returns `{"status":"ok",...}` and
   `/docs` loads.

**Plan note:** `render.yaml` sets the web service to **Starter** on purpose —
the AI-insight embedding model (sentence-transformers/torch) needs more RAM
than the 512 MB free tier, and the persistent disk (so the ChromaDB index and
model cache survive restarts) requires a paid instance. For a free-tier demo
of just the screener, set the web service `plan: free` and remove the `disk:`
block — the core stock/news features work; the KB just re-downloads its model
on each cold start.

**Postgres:** the free Render database expires after ~90 days — fine for a
portfolio, upgrade for anything longer-lived. Migrations run automatically on
startup (`init_db()` creates the tables on the fresh Postgres).

> Prefer Docker or Railway? A ready [`backend/Dockerfile`](backend/Dockerfile)
> is included — point any Docker-based host at the `backend/` directory and
> mount a volume at `/var/data` for the ChromaDB/model cache.

---

## 2. Frontend on Vercel

1. In Vercel: **Add New → Project**, import the same repo.
2. **Set Root Directory to `frontend`** (this is a monorepo — Vercel must
   build from there). Framework preset auto-detects as Next.js.
3. Add one environment variable:
   | Key | Value |
   |---|---|
   | `NEXT_PUBLIC_API_URL` | `https://<your-render-service>.onrender.com` |
4. Deploy. Then go **back to Render** and set `CORS_ORIGINS` to your new
   Vercel URL (as a JSON array) so the browser calls aren't blocked.

---

## 3. Post-deploy checklist

- [ ] `GET /` on the Render URL returns `{"status":"ok"}`.
- [ ] Vercel site loads; searching a ticker renders a chart (backend reachable).
- [ ] Sign in with a username on **/watchlist**, add a ticker, refresh the
      page — it persists (Postgres working).
- [ ] Open a ticker's **AI insight** — a grounded summary appears, follow-ups
      work (Groq + ChromaDB working).
- [ ] Sign in as a different username in a private window — separate,
      isolated watchlist (per-user data working).

## Environment variables reference

**Backend** (Render): `SECRET_KEY`, `DATABASE_URL`, `LLM_PROVIDER=groq`,
`GROQ_API_KEY`, `GROQ_MODEL`, `LLM_TEMPERATURE`, `CORS_ORIGINS`,
`CHROMA_PERSIST_DIR`, `HF_HOME`, and optionally `NEWS_API_KEY`,
`REDDIT_CLIENT_ID`/`REDDIT_CLIENT_SECRET` for social sentiment.

**Frontend** (Vercel): `NEXT_PUBLIC_API_URL`.

## Security notes

- `SECRET_KEY` signs the auth tokens — never reuse the dev default in
  production. Render's `generateValue: true` handles this.
- Rotate any API key that has ever been shared in plaintext (e.g. in chat or
  a screenshot), including the Groq key.
- The username login is intentionally lightweight (an unguessable passphrase
  is optional per account). If you later want stronger auth, the backend is
  structured so a "Sign in with Google" (OAuth) provider can be added
  alongside it without touching the per-user data model.
